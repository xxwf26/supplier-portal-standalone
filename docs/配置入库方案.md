# 配置入库方案 — 系统配置成为唯一数据源

> 状态：阶段1已实施　|　日期：2026-06-17
> 删除策略：**禁止删除**（有画师在用则不允许删，属阶段2）
> 供应商类型：**沿用现有体系**（label=中文展示、value=英文枚举、数据库存"个人/工作室/公司"），不在本方案改动。

## 背景与目标

理想终态：一条画师数据的字段与详情页完全对应；每个字段的细分选项由系统配置统一管理。
**在系统配置中增删某字段的细分标签，左侧筛选与详情页的对应选项同步增删（系统配置成为唯一数据源）。**

## 当前漏洞

1. **配置不在数据库，在浏览器 localStorage**（`__admin_filter_config`）。不跨设备/用户、清缓存即丢、各看各的。
   - 后端其实已写好一套完整 DB 配置系统（`filter_config` 表 + `ConfigService` + `ConfigController` + admin 守卫），但前端从未接入，是死代码。
2. **画师字段值 ↔ 配置选项无约束（无外键）**。删配置选项 → 画师旧值变孤儿，详情页仍显示。← 痛点 1 根源。
3. **多值字段用「、」拼成字符串塞单列**（`subCategory`=擅长风格、`cooperationType`=合作类型）。难精确同步删除、难精确筛选/统计。
4. **字段命名挪用**：`subCategory` 实为擅长风格、`entityType` 实为历史参与项目。
5. **删除无保护、无策略**。

## 终态架构

```
filter_config 表(DB) — 唯一数据源
  字段: id / category / label / value / color / sortOrder / enabled / createdAt
        │  /api/config/filters
  ┌─────┼───────────┬──────────┬───────────┐
系统配置页   左侧筛选   详情页选项   新建/编辑下拉
 (增删改)    (读)       (读)        (读)
```
category 取值：`supplierType / cooperationType / style / cooperationStatus / project`。

## 实施阶段

### 阶段 1｜配置入库（已实施）
- 启用已有的 `filter_config` 表 + `ConfigService`。
- 种子脚本 `create-filter-config-2026-06-17.sql`：建表 + 灌入现有默认配置（每个库执行一次）。
- 前端 `useFilterOptions`、`SystemConfigPage` 改为读写 `/api/config/filters`，退役 localStorage。
- 加载失败回退默认值（表未建也不崩）。
- 交付：配置入库、跨设备/用户共享、筛选/详情页/下拉全部同步。

### 阶段 2｜禁止删除 + 引用保护（解决痛点 1，待做）
- 删除接口先做使用量统计（扫描画师表，数引用该 value 的记录）：
  - 用量 = 0 → 允许删除。
  - 用量 > 0 → **拒绝删除**，返回正在使用的画师名单；前端提示「『古风』正被 7 个画师使用，请先修改后再删除」。
- **编辑同样保护**：`label` 可自由改；`value` 在被使用时锁定/校验（改 value 等于删旧值会造孤儿）。
- ⚠️ 多值字段使用量统计不能用简单 LIKE（`"复古风、古风"` 用 `LIKE '%古风%'` 会误中），须按「、」切分精确比对。

### 阶段 3｜字段对齐 + 多值规范化（终态，待做）
- 命名对齐：`subCategory→擅长风格`、`entityType→历史项目`。
- 多值字段（风格、合作类型）从「、拼接字符串」迁到关联表，实现真正引用完整性与精确同步删除。

## 涉及改动

- **后端**：复用 `server/src/database/filter-config.schema.ts`、`modules/config/`；`drizzle.config.ts` 纳入 filter-config schema。阶段2 给 `config.service.delete` 加使用量校验。
- **前端**：`client/src/hooks/useFilterOptions.ts` 改调 API；`client/src/pages/SystemConfigPage.tsx` 改调 API CRUD。
